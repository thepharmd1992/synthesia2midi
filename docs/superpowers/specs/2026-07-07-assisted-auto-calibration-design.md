# Assisted Auto-Calibration Design

## Goal

Reduce calibration failures by automating the steps after the user draws a keyboard bounding box on a good unlit frame.

V1 keeps the user responsible for selecting the keyboard region. The app then detects overlays, captures unlit reference data, scans the video for lit key examples, and proposes lit exemplar colors for the existing detection pipeline.

## Non-Goals

- No fully automatic keyboard ROI discovery in V1.
- No automatic octave-scaling correction in V1.
- No new detection backend or model dependency.
- No silent overwrite of calibration data without user confirmation.
- No assumption that legacy `LW`, `LB`, `RW`, and `RB` names mean physical left or right keyboard position.

## Current Findings

The existing `AutoDetectAdapter` is reliable when it receives a close keyboard ROI. On the Game of Thrones reference video, the saved target calibration has:

- 88 overlays.
- Overlay bounds around `x=15..1901`, `y=870..1067`.
- Source frame and ROI generated by the existing auto-detect flow.
- Lit exemplar colors:
  - `LW = 133,166,203`
  - `LB = 72,110,170`
  - `RW = 243,176,68`
  - `RB = 243,131,46`

The same video also shows why full automatic frame selection is risky. The keyboard is visible early during the fade-in, but that is not the settled unlit lighting state. V1 avoids this by requiring the user to draw the box on a frame where the keyboard is fully visible and unlit.

## Terminology

The legacy exemplar slots remain `LW`, `LB`, `RW`, and `RB` for compatibility.

For assisted calibration, these slots mean:

- `LW`: color family A on white keys.
- `LB`: color family A on black keys.
- `RW`: color family B on white keys.
- `RB`: color family B on black keys.

They do not mean physical left/right position. A single key can be lit by either color family over the course of a video.

## User Flow

1. User opens the calibration wizard.
2. User chooses the existing auto-detect region selection path.
3. User draws a bounding box around the keyboard on a frame where the keyboard is visible and unlit.
4. The app runs the existing key detector inside the selected ROI.
5. The app checks whether the selected frame appears to contain lit keys.
6. If the frame looks clean, the app captures unlit reference color and histogram data immediately.
7. If the frame may contain lit keys, the app shows a soft warning that names likely lit notes and lets the user either cancel or continue anyway.
8. The app offers to scan the video for lit exemplar colors.
9. The app scans frames using the detected overlay ROIs and derives candidate color families.
10. The app presents a confirmation summary before saving exemplar updates.

## Unlit Frame Guard

The unlit-frame guard should be reusable outside the assisted flow. It should also protect the existing "Calibrate Unlit All Keys" action.

Inputs:

- current RGB frame
- detected overlays
- optional previous unlit reference data

Output:

- `clean`: no strong lit candidates found
- `warning`: likely lit overlays with note names and confidence
- `unknown`: insufficient evidence

Detection strategy:

- Compute per-overlay RGB and HSV summaries.
- Separate white-key and black-key overlays.
- Build robust per-key-color baselines from median color/chroma across overlays.
- Flag overlays that are strong chroma and RGB outliers relative to their key-color group.
- When existing unlit references exist, also compare current overlay color to its saved unlit reference.
- Report only high-confidence outliers in the user message, for example `E4` or `G4`.

The warning is soft. The user can continue because some videos may have unusual lighting, glare, or colored key skins.

## Lit Exemplar Scan

The scan should use existing overlay rectangles rather than full-frame vision.

Algorithm:

1. Start from the frame used for ROI selection and unlit capture.
2. Scan forward through the video at a coarse stride, initially every 5 to 10 frames.
3. For each sampled frame, compute average RGB/HSV and histogram features for each overlay ROI.
4. Compare each overlay against its unlit reference.
5. Keep lit candidates when color delta, chroma, and persistence pass thresholds.
6. Refine promising coarse candidates by scanning nearby frames one by one.
7. Store the best candidate sample per event, including frame index, overlay key ID, note name, key color, RGB, HSV, and confidence.

This is computationally bounded. A long video can be scanned using 88 small overlay rectangles per sampled frame, with a cancelable progress dialog.

## Color Family Assignment

The assistant should assign exemplar slots by color family, not position.

Candidate processing:

- Cluster lit candidates by hue/chroma in a deterministic color space.
- Pair black-key candidates to the nearest white-key family by hue when possible.
- Prefer high-confidence, saturated, persistent samples.
- Treat white-key and black-key exemplars separately because black-key lit colors can be darker shades of the same family.
- Use deterministic tie breakers: confidence, earliest frame, then hue ordering.

Assignment:

- One strong family with white and black examples:
  - fill `LW` and `LB`
  - disable `RW` and `RB`
- Two strong families:
  - assign family A to `LW` and `LB`
  - assign family B to `RW` and `RB`
- Missing black or white exemplar:
  - leave the missing slot unchanged or disabled only after user confirmation
  - show the missing slot in the summary so the user can manually complete it

The scan should not create fake second-family colors. The existing `exemplar_key_type_enabled` state should represent absent families.

## UI Design

V1 can use a modal progress and confirmation flow.

After the user draws the keyboard box and auto-detection succeeds:

- show any unlit-frame warning before saving unlit references
- show a progress dialog while scanning for lit exemplars
- allow cancel
- show a final summary dialog

The summary should include:

- detected overlay count
- baseline frame used for unlit calibration
- found exemplar slots and RGB values
- missing exemplar slots
- likely color-family count
- confidence level
- whether disabled exemplar slots will be saved

If accepted, save through the existing config path and refresh the control panel.

Later versions can move the video scrubber to each relevant frame during the scan. V1 should not depend on visible scrubbing.

## Error Handling

- If key auto-detection fails, keep the existing failure path.
- If the unlit-frame guard warns, let the user cancel or continue.
- If no lit candidates are found, save overlays and unlit data only, then tell the user to calibrate lit exemplars manually.
- If only partial exemplars are found, present partial results and let the user choose whether to apply them.
- If the scan is canceled, do not write exemplar changes.
- If saving fails, leave app state dirty and show the existing save failure path.

## Data Flow

The proposed implementation boundary is:

```text
CalibrationWizard / controller
  -> AutoDetectAdapter
  -> AssistedCalibrationAnalyzer
       -> UnlitFrameGuard
       -> ExemplarScanner
       -> ColorFamilyAssigner
  -> AppState overlays and DetectionConfig
  -> ConfigManager save
```

`AssistedCalibrationAnalyzer` should return a proposal object. UI code applies the proposal only after user confirmation.

## Testing Strategy

Unit tests:

- unlit-frame guard flags saturated outlier overlays
- unlit-frame guard returns clean for normal unlit keyboard fixtures
- exemplar scanner finds candidates from synthetic frame sequences
- color-family assignment handles two-color, one-color, missing-black, and same-hue-different-value cases
- proposal application updates existing `LW/LB/RW/RB` and `exemplar_key_type_enabled` state correctly

Integration tests:

- auto-detect region selection can capture unlit references after overlays are generated
- existing manual unlit calibration path shows a soft warning when likely lit overlays are present
- canceled scan does not write exemplar changes
- accepted scan saves through the existing config path

Local exploratory gate:

- run the analyzer against the Game of Thrones local video
- compare generated overlay bounds against the saved target overlays
- compare proposed exemplar RGB values against the saved target INI
- treat octave transpose as out of scope

## Implementation Phases

### Phase 1. Offline analyzer

Build the analyzer as pure services with no UI writes. It should produce a calibration proposal from a frame source, overlays, and baseline frame.

### Phase 2. Unlit-frame guard

Add the reusable guard and wire it into both assisted calibration and the existing unlit calibration action.

### Phase 3. Assisted wizard flow

Add the scan and confirmation flow after successful manual ROI auto-detection.

### Phase 4. Local video validation

Run the analyzer against the Game of Thrones reference video and tune thresholds until the proposal is close to the saved INI without hard-coding the video.

### Phase 5. Multi-video validation

When more videos are available, evaluate failure modes before attempting full automatic ROI discovery.

## Open Decisions

- Exact confidence thresholds should be selected from prototype measurements.
- The confirmation dialog wording should avoid "left" and "right" where the concept is really color family.
- Video scrubber movement during scan is useful but not required for V1.
